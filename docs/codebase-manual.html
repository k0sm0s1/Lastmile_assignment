System map

The live ROS graph once everything is running. Boxes are processes (nodes); labels on the arrows are the topics or actions between them. The teal path is the Task 3 chain, from a waypoint to wheel motion.

Offline, before any of this runs: preprocess_cloud.py → cloud_to_mesh.py → make_collision_mesh.py produce the Gazebo meshes, and cloud_to_occupancy_grid.py → make_nav_map.py produce the two maps.

Start-up order

What scripts/run_demo.sh does, in sequence. The order matters: each stage needs the one before it.

  1. Stop anything still running, restart the ROS CLI daemon, and export the UDP-only DDS profile.
  2. Gazebo + world + robot (spawn_world.launch.py). Then wait until /odom has a publisher, which proves the robot actually spawned.
  3. Maps, AMCL and Nav2 (bringup_nav2.launch.py). The lifecycle manager configures and activates each server. The script waits until every node reports active and restarts the bring-up once if it stalls.
  4. robot_state_manager. The pose topic starts at 10 Hz and waypoints are accepted from here on.
  5. Web pages: the dashboard always, plus the delivery page with DELIVERY=1. Then it prints every Nav2 node's state.

Repository root

Top-level files that describe, configure and document the workspace. The repo is a colcon workspace: clone it, run colcon build at the root, and the seven packages under src/ get built into install/.

README.md

Config417 lines

The assignment write-up. It has the measured results (tables copied from test logs), a section for each task, the full debugging table, the obstacle and delivery modes, how to run everything, and the known limitations.

  • Every number in it comes from scripts/waypoint_test.sh, obstacle_test.py or delivery_test.py output, never from expectation.
  • The debugging table (symptom, real cause, fix) is the part reviewers read most closely.

.gitignore

Config17 lines

Keeps colcon output (build/, install/, log/), Python caches and the two large point-cloud files out of git.

  • data/map_ros_cloud.ply (72 MB raw scan) and data/cleaned_cloud.ply are excluded. They are inputs to the offline scripts and can be regenerated or re-downloaded.

requirements.txt

Config7 lines

Python packages for the offline scripts only: open3d 0.20, numpy, scipy, pillow. The ROS nodes need nothing beyond ROS 2 Humble's own Python packages, plus numpy, scipy and OpenCV, which ship with Ubuntu 22.04's ROS install.

  • open3d is only needed by preprocess_cloud.py and cloud_to_mesh.py. The occupancy-grid builder parses the PLY itself with numpy.

config/fastdds_udp_only.xml

Config23 lines

A Fast DDS profile that turns off the shared-memory transport and uses UDPv4 only. Every script exports it through FASTRTPS_DEFAULT_PROFILES_FILE.

  • Why it exists: under WSL2 the shared-memory transport silently stopped delivering AMCL's map→odom transforms to the Nav2 servers. Their TF buffers froze at the first transform, so the planner kept planning from the spawn point.
  • DDS is the middleware under ROS 2 topics. Changing its transport changes nothing in the node code.

data/floor_transform.json

Asset27 lines

The rigid transform that levels the scan: a 3×3 rotation that turns the fitted floor normal onto +z, then a z offset that puts the floor at z = 0. Written by preprocess_cloud.py and read by cloud_to_occupancy_grid.py, so the mesh and the 2D map share exactly the same frame.

  • Floor normal in the raw scan: (−0.0166, 0.0143, 0.9998), a tilt of about 1.3°. The offset is 0.019 m.

docs/

Asset

Media referenced by the README: demo.mp4 (the 3-waypoint run from the chase camera), demo_obstacles.mp4 (the slalom), still frames of both, and delivery.jpg (a screenshot of the delivery page).

  • The videos are produced by scripts/record_demo.sh. Nothing here is hand-edited.

windows/*.bat

Optional extra

Double-click launchers for Windows. Each one calls wsl -e bash -lc "… bash scripts/run_demo.sh" with a different pair of flags, opens the browser pages when the stack is ready, then keeps the window open with sleep infinity so the WSL session (and the ROS processes in it) stays alive.

  • START_1_BASIC: no flags. START_2_OBSTACLES: OBSTACLES=1. START_3_DELIVERY: DELIVERY=1. START_EVERYTHING: both. STOP_EVERYTHING: run_demo.sh stop.
  • They assume the workspace lives at ~/lastmile_ws inside the default WSL distro.

scripts/: the offline pipeline

Run once, outside ROS, in this order. They turn the raw scan into the two assets the robot software needs: a 3D mesh for Gazebo and a 2D occupancy grid for Nav2. They also produce the bounded planning map. All of them write into src/, so the ROS packages pick the results up at build time.

scripts/preprocess_cloud.py

Offline script128 lines

Stage 1. It loads data/map_ros_cloud.ply (2,338,923 points, no faces), cleans it, and re-expresses it in a frame where z = 0 is the real floor. Outputs data/cleaned_cloud.ply and data/floor_transform.json.

  • Voxel downsample at 3 cm: one point per 3 cm cube, about 10× fewer points and still enough detail for walls.
  • Statistical outlier removal (20 neighbours, 2.0 σ) drops isolated noise points.
  • RANSAC floor fit: only on the bottom 40 % of the height range. Run on the whole cloud, RANSAC locks onto a wall, because walls have more area than the floor in a corridor.
  • Rodrigues rotation turns the floor normal onto +z. Then the floor height is taken as the mode of a histogram of the low points and subtracted.

scripts/cloud_to_mesh.py

Offline script76 lines

Stage 2a. Surface reconstruction: point cloud → triangle mesh environment.obj (150k triangles). This is a real reconstruction, not a format conversion, because the scan has zero faces.

  • Normals are re-estimated (radius 0.1 m, 30 neighbours) and oriented consistently, because Poisson needs globally consistent normals.
  • Poisson reconstruction at depth 9 builds a watertight surface.
  • Density trim: Poisson also returns a density per vertex. Low density means Poisson invented surface across a hole (a doorway or an unscanned gap), so the lowest 3 % is deleted.
  • Cleanup (degenerate, duplicate and non-manifold elements), then quadric decimation to 150k triangles so Gazebo's physics stays real-time.

scripts/make_collision_mesh.py

Offline script71 lines

Stage 2b. From environment.obj it writes two derived meshes. environment_collision.obj is walls only. environment_visual.obj is the ceiling cut away above 2 m, so the Gazebo camera can see in.

  • Pure numpy: it parses the OBJ, computes each triangle's normal and top height, and writes the kept faces with re-indexed vertices.
  • Why remove the floor: the reconstructed floor is bumpy (±8 cm). The TurtleBot rested on bumps with its wheels unloaded and would not move. model.sdf replaces the floor with a flat plane.
  • Walls keep everything above 0.12 m, so the lidar (at about 0.27 m) still sees them.

scripts/cloud_to_occupancy_grid.py

Offline script147 lines

Stage 3. Projects the 3D scan into Nav2's 2D map: lastmile_map.pgm + .yaml, 529 × 367 cells at 5 cm. This is the most important asset for localization quality.

  • Reads the PLY with numpy (no open3d) and applies floor_transform.json.
  • Local floor height: the SLAM floor drifts ±10 cm across the site, so heights are measured above a local floor. That floor is the 10th percentile of low points in 0.25 m tiles, with holes filled and a 3×3 median.
  • Obstacle = vertical structure: a cell is occupied only if it has ≥ 40 points spread over ≥ 8 distinct 5 cm height bins between 0.12 and 1.60 m (or ≥ 150 points). Walls pass easily. The ghost haze around the scan start does not.
  • Free = floor actually observed, connected to the spawn at (0, 0). Everything never seen stays grey (unknown, 205).
  • Output pixel values: 254 free, 0 occupied, 205 unknown. The yaml sets free_thresh: 0.25, so map_server loads the grey cells as free (needed for half-scanned floor).

scripts/make_nav_map.py

Offline script79 lines

Builds the bounded planning map lastmile_nav_map.pgm. It is identical to lastmile_map.pgm inside the building, with everything outside the building outline set to occupied. Only the costmaps use it; AMCL keeps the honest map.

  • Why: because unknown loads as free, the planner could route through a scan gap in a wall and drive around outside the building.
  • "The building" is the same cleaned outline the delivery page draws (floorplan.clean_floor + regularize), grown by MARGIN = 7 cells (35 cm). A 15 cm margin trimmed half-scanned floor in the north arm and made the robot stall there.
  • CORNER_KEEPOUTS: two 0.25 m discs on the wall corners at the mouth of the north arm, so DWB can't cut the corner into the wall's inscribed zone.
  • Deterministic: it regenerates the committed file byte-for-byte.

scripts/: running and testing

Shell and Python tools that start the live system and measure it. The measured tables in the README come from these.

scripts/run_demo.sh

Runtime node69 lines

One-command bring-up of the whole stack, used by every launcher. It starts four stages in order and waits until each one is actually ready before starting the next.

  • Environment flags: GUI=1 opens the Gazebo window, OBSTACLES=1 spawns the boxes and uses the obstacle params, DELIVERY=1 adds the 8081 page, and stop kills everything.
  • Order: (1) Gazebo + robot, then wait for /odom (up to 150 s, because the mesh is slow to load with the GUI). (2) map servers + AMCL + Nav2, then wait for all lifecycle nodes to be active, retrying once if bring-up stalls. (3) robot_state_manager. (4) the dashboard, plus delivery if requested.
  • Each process runs under setsid nohup with its log in ~/lastmile_logs/. It exports the UDP-only DDS profile and TURTLEBOT3_MODEL=waffle.
  • It calls stop_all first, so running it again restarts cleanly.

scripts/ros_wait.py

Runtime node59 lines

A small readiness checker that doesn't depend on the ros2 CLI daemon, which got stuck under WSL2. It has three modes: topic (wait for a publisher), active (wait for lifecycle nodes) and states (print them).

  • It calls each node's /<name>/get_state service (lifecycle_msgs/GetState) directly. Exit code 0 means ready and 1 means timed out.

scripts/waypoint_test.sh

Test / tooling23 lines

The Task 3 acceptance test. It sends waypoints through /robot/next_waypoint, the same path a user would take, then records the node's localized pose and Gazebo's ground-truth pose at each arrival.

  • It waits for a new goal id to reach a terminal state, so it never mistakes the previous goal's result for this one.
  • Ground truth comes from gz model -m turtlebot3_waffle -p. The difference from the node's pose is the AMCL error reported in the README.

scripts/obstacle_test.py

Test / tooling89 lines

Obstacle-mode check. It sends one goal (default 12.5, 0), logs ground truth from /gazebo/model_states, then reports the result, the closest surface clearance to each box, which side the robot passed on, and what obstacle_mapper detected.

  • Clearance = distance from the robot centre to the box surface minus the 0.22 m robot radius. BOXES must match spawn_world.launch.py.

scripts/delivery_test.py

Test / tooling58 lines

Drives a full delivery mission through the delivery page's own HTTP API. It starts the mission, then presses Loaded and Unloaded as soon as the page enables them, and prints the timeline.

  • Usage: python3 scripts/delivery_test.py library server, where the arguments are place ids from PLACES.

scripts/record_demo.sh

Test / tooling31 lines

Records a demo video. It does a fresh bring-up, spawns the demo_camera model, starts record_demo, runs waypoint_test.sh, then converts the MJPG .avi to .mp4 with OpenCV.

  • It records to .avi first because an MP4 file is only valid once it is finalised, and an abort at shutdown had zeroed the MP4 header.

What every ROS 2 package contains

These small files appear in every package below. Here's what each one is for, explained once.

package.xml

Package plumbing

The package manifest (format 3): name, version, maintainer, licence, dependencies and the build type. ament_cmake is for packages that only install files. ament_python is for Python nodes. colcon and rosdep read it.

CMakeLists.txt

Package plumbing

Only in the ament_cmake packages here (description, navigation, bot_description). They contain no code to compile, just install(DIRECTORY … DESTINATION share/${PROJECT_NAME}). That copies worlds, models, maps, params and launch files where get_package_share_directory() finds them.

setup.py / setup.cfg

Package plumbing

The Python equivalent for the ament_python packages. data_files installs launch files and web assets. entry_points → console_scripts turns a main() function into an executable that ros2 run and launch files can start. setup.cfg tells setuptools to put those executables in lib/<package>, where ROS looks.

resource/<package> · <package>/__init__.py

Package plumbing

Empty marker files. resource/<name> registers the package in the ament index, so ROS can find it. __init__.py makes the folder an importable Python module.

src/lastmile_description: Task 1 (the world)

The Gazebo side: the world file, the scanned-building model, the obstacle boxes, and the launch file that spawns the robot at (0, 0, 0).

src/lastmile_description/launch/spawn_world.launch.py

Launch100 lines

Starts Gazebo Classic (gzserver, plus gzclient if gui:=true) with lastmile_world.world, spawns the TurtleBot3 Waffle at (0, 0, 0.10), and starts TurtleBot3's robot_state_publisher.

  • The robot is dropped from 10 cm so its wheels settle instead of starting inside the floor. -timeout 120 is there because loading the mesh with the GUI can take more than 30 s (the default), and the robot then silently failed to spawn.
  • robot_state_publisher provides base_footprint → base_link → base_scan. Without it AMCL cannot place a single laser scan and never publishes map → odom. That was the first bug in the project.
  • It prepends the package's models/ folder to GAZEBO_MODEL_PATH, so model://scanned_environment resolves.
  • obstacles:=true spawns three obstacle_box models in a slalom. spawn_turtlebot3:=false lets a different robot be used instead.

src/lastmile_description/worlds/lastmile_world.world

Asset50 lines

The SDF 1.7 world: ODE physics at a 1 ms step, a sun light, the start camera pose, the gazebo_ros_state plugin, and one <include> of model://scanned_environment at the origin.

  • Gazebo Classic was chosen over Gazebo Sim because it's the best-supported Humble + TurtleBot3 + Nav2 combination, and its OGRE1 renderer works over WSLg.
  • libgazebo_ros_state.so exposes /gazebo/get_entity_state and set_entity_state. The chase camera and the ground-truth readings use them.

src/lastmile_description/models/scanned_environment/model.sdf

Asset52 lines

The building as one static model. Visual is environment_visual.obj (ceiling cut). Collision is environment_collision.obj (walls only) plus an analytic flat <plane> for the floor.

  • This visual/collision split is what made the robot drive at all. The bumpy reconstructed floor gave unstable wheel contact.

src/lastmile_description/models/scanned_environment/meshes/*.obj

Asset

environment.obj (150k triangles, the full reconstruction), environment_collision.obj (127k, floor removed) and environment_visual.obj (98k, ceiling removed). Units are metres, with the floor at z = 0.

src/lastmile_description/models/scanned_environment/model.config

Package plumbing14 lines

Gazebo model metadata: name, version, and which SDF file to load.

src/lastmile_description/models/obstacle_box/model.sdf

Asset23 lines

A static 0.4 × 0.4 × 0.6 m orange box used by obstacle mode. It is deliberately absent from both maps.

src/lastmile_description/models/demo_camera/model.sdf

Asset26 lines

A kinematic, gravity-free camera (960×540 at 10 Hz) with the gazebo_ros_camera plugin publishing /demo_cam/chase/image_raw. record_demo moves it behind the robot every frame. It's only used for recording videos.

src/lastmile_navigation: Task 2 (map, localization, Nav2)

Everything Nav2 needs: the maps, the parameter files, and the bring-up launch file that starts the map servers, AMCL and the Nav2 servers under one lifecycle manager.

src/lastmile_navigation/launch/bringup_nav2.launch.py

Launch104 lines

Starts map_server (the real map on /map), nav_map_server (the bounded map on /nav_map), amcl, controller_server, planner_server, behavior_server, bt_navigator and lifecycle_manager_navigation, plus obstacle_mapper when obstacles:=true.

  • Lifecycle nodes: Nav2 servers start unconfigured. The lifecycle manager (autostart: true) steps each one through configure → activate in order. ros_wait.py checks exactly these states.
  • A PythonExpression picks nav2_params_obstacles.yaml when obstacles:=true, and nav2_params.yaml otherwise. RewrittenYaml loads it.
  • The same map_server executable runs twice, under two node names with different yaml_filename and topic_name values.

src/lastmile_navigation/maps/lastmile_map.pgm + .yaml

Asset

The honest 2D map from cloud_to_occupancy_grid.py: 529 × 367 cells at 0.05 m, with origin (−5.19, −6.25). AMCL localizes against this map.

  • The yaml fields: resolution is metres per pixel. origin is the world position of the bottom-left pixel. mode: trinary maps pixels to free, occupied or unknown using occupied_thresh 0.65 and free_thresh 0.25. With 0.25, grey 205 (p = 0.196) loads as free.

src/lastmile_navigation/maps/lastmile_nav_map.pgm + .yaml

Asset

The bounded planning map from make_nav_map.py. It is published on /nav_map and read by both costmaps' static layers. Same size, origin and resolution as the honest map.

src/lastmile_navigation/params/nav2_params.yaml

Config242 lines

All Nav2 and AMCL parameters for the default mode. This is where most of the project's tuning lives.

  • AMCL: likelihood-field laser model, 500–2000 particles, laser_min_range 0.3 to ignore hits on the robot's own body, and an initial pose seeded at (0, 0, 0) with set_initial_pose: true.
  • Controller: DWB at 10 Hz (20 Hz was routinely missed), max 0.22 m/s, xy goal tolerance 0.25 m.
  • Costmaps: static_layer (from /nav_map) + inflation_layer (0.55 m), robot radius 0.22 m. The stock laser ObstacleLayer was removed because its tf2 MessageFilter deadlocked the costmaps at start-up under WSL2.
  • Planner: NavFn (Dijkstra) with allow_unknown: false.
  • bt_navigator: default_server_timeout: 500 ms. The 20 ms default caused false recoveries (stop-and-go) under CPU load.

src/lastmile_navigation/params/nav2_params_obstacles.yaml

Config263 lines

Identical to nav2_params.yaml, except both costmaps get a third layer, obstacle_map_layer. It is a second StaticLayer fed by /obstacle_map from the lidar node, with use_maximum: true.

  • A StaticLayer just copies a grid, so it cannot deadlock the way the laser ObstacleLayer did.

src/lastmile_navigation/params/nav2_params_lastmile_bot.yaml

Optional extra244 lines

A variant for the optional lastmile_bot robot. The only substantive difference is robot_radius: 0.30 instead of 0.22, for its wider body. It was not part of the verified runs.

src/robot_state_manager: Task 3 (the custom node)

The assignment's custom node, written in rclpy. It has four jobs: publish the pose at 10 Hz, receive waypoints, drive to them through Nav2's action, and watch /cmd_vel against speed thresholds.

src/robot_state_manager/robot_state_manager/robot_state_manager_node.py

Runtime node316 lines

The RobotStateManager node. It also publishes /robot/nav_status (JSON), which both web pages are built on.

  • 1. Position publisher: /robot/current_xyz (Float32MultiArray [x, y, z]). The pose is the localized one, from TF map → base_footprint, which is AMCL composed with odometry. Raw /odom is only a fallback. The timer runs on the wall clock, because a sim-time timer gave only about 7.5 Hz real time with Gazebo below real-time speed.
  • 2. Goal receiver: /robot/next_waypoint (PoseStamped). A blank frame defaults to map, the stamp is set to 0 (meaning the latest transform), and an all-zero quaternion is fixed to w = 1.
  • 3. Nav2 interface: an ActionClient for nav2_msgs/action/NavigateToPose (the assignment's "MapsToPose" doesn't exist). Feedback gives distance remaining, recoveries and time. A new waypoint pre-empts the old one, and a sequence number drops stale results.
  • Success verification: on SUCCEEDED the node compares its localized pose with the goal and flags anything more than 0.5 m away as unverified. This guards against a Humble controller bug that reported "Reached the goal!" while the robot hadn't moved.
  • 4. Command monitor: on /cmd_vel it logs every excursion above 0.20 m/s or 0.80 rad/s (warnings throttled to 0.5 s) and counts them.
  • Extra: /robot/cancel (Empty) cancels the active goal.

src/robot_state_manager/launch/robot_state_manager.launch.py

Launch28 lines

Starts the node with launch arguments for linear_velocity_threshold (0.20), angular_velocity_threshold (0.80), publish_rate_hz (10) and use_sim_time. For example: ros2 launch robot_state_manager robot_state_manager.launch.py linear_velocity_threshold:=0.15.

src/robot_state_manager/setup.py / package.xml

Package plumbing

The entry point is robot_state_manager_node = robot_state_manager.robot_state_manager_node:main. It depends on rclpy, std_msgs, geometry_msgs, nav_msgs, nav2_msgs, action_msgs and tf2_ros.

src/lastmile_obstacles: live obstacle detection

One node that adds lidar-based obstacle avoidance back into Nav2 without the laser layer that froze.

src/lastmile_obstacles/lastmile_obstacles/obstacle_mapper.py

Runtime node237 lines

It turns /scan + TF + the maps into /obstacle_map: the bounded walls plus every lidar return that isn't a known wall. It keeps an evidence grid on the same cells as the map.

  • For each scan (at most 5 Hz, every 3rd beam), each beam is projected into the map through the latest map ← base_scan transform. There is no message filter to deadlock.
  • Cells a beam passes through lose 1 evidence, which clears boxes that have moved. The cell a beam ends in gains 3, unless it is within 30 cm of a mapped wall (AMCL is only good to about 15 cm) or is unscanned space.
  • A cell with evidence ≥ 6 (two consistent scans) is an obstacle, grown by 2 cells because the lidar only sees the near face.
  • Publishes latched /obstacle_map at 2 Hz, and a JSON cluster list on /obstacle_mapper/obstacles (the orange squares on the web pages).
  • It carries the /nav_map walls under its detections. Each /obstacle_map update re-sizes the global costmap, which wiped the other static layer; carrying the walls here keeps the costmap correct.

src/lastmile_dashboard: web pages and the recorder

Two web apps and a video recorder. Each web app is one rclpy node running a standard-library HTTP server: no rosbridge and no npm. The node serves the page, streams state with Server-Sent Events, and turns POST requests into ROS messages.

src/lastmile_dashboard/lastmile_dashboard/dashboard_node.py

Runtime node378 lines

The engineering dashboard on :8080. It subscribes to /map, /robot/current_xyz, /robot/nav_status, /cmd_vel, /plan, /scan, /amcl_pose and /obstacle_mapper/obstacles. It publishes /robot/next_waypoint, /robot/cancel and /initialpose.

  • Endpoints: GET /map.png (the map rendered by a hand-written PNG encoder using zlib), /api/map, /api/stream (SSE at about 10 Hz), and POST /api/goal, /api/cancel, /api/initialpose.
  • Health: it polls each Nav2 node's lifecycle state and measures the age of the map→odom transform, which shows whether AMCL is alive.
  • Lidar points are projected into the map through TF, so you see what the robot sees.

src/lastmile_dashboard/web/index.html

Web UI291 lines

The dashboard page: one file with vanilla JS and a canvas. It draws the map PNG, robot, plan, lidar points and goal. Click to send a goal (drag to set the heading), use "set pose" mode to re-seed AMCL, and watch the live xyz rate, cmd_vel bars against the thresholds, nav state, health and history.

src/lastmile_dashboard/lastmile_dashboard/delivery_node.py

Runtime node460 lines

The delivery app on :8081. It holds the mission state machine on the server, so a page refresh never loses progress, and it drives every leg through the Task 3 node.

  • States: to_pickup → at_pickup →[Loaded]→ to_dropoff → at_dropoff →[Unloaded]→ returning → delivered, plus problem (Retry / Return to dock).
  • Each leg publishes a goal on /robot/next_waypoint and binds to the first new goal id at that target. It counts as arrived only when /robot/nav_status says succeeded and verified.
  • Auto un-stick: when a leg aborts, it drives 15 cm forward or back (whichever gains more wall clearance on the planning map) by publishing /cmd_vel directly, then resends the leg. It does this at most twice.
  • PLACES: 10 named stops, each checked at start-up against the reachable mask (clearance ≥ 0.35 m, connected to the dock). /api/snap moves a tapped point to the nearest reachable cell.
  • ETA comes from an exponential moving average of progress speed. Detected obstacles are shown only when they're inside the building outline.

src/lastmile_dashboard/lastmile_dashboard/floorplan.py

Runtime node135 lines

Turns the noisy occupancy grid into a clean, presentation-only floor plan: sealed gaps, straight walls and a vector outline. The delivery page draws it, and make_nav_map.py reuses it as "the building".

  • clean_floor: free cells → morphological closing (disk, 9 cells) to seal gaps → fill holes → opening (3) to remove spurs → keep the component that contains the dock.
  • regularize: closing then opening with square elements (13, 9), which straightens walls to the axes.
  • outline: cv2.findContours → approxPolyDP (2.5 cells) → _orthogonalize, which snaps near-horizontal and near-vertical edges within 14° to exact axes.

src/lastmile_dashboard/web/delivery.html

Web UI475 lines

The delivery page, with an Apple-style light UI. It draws the vector floor plan on a canvas (floor, walls, numbered place dots, dock, route line, robot dot with heading cone, A and B pins) and runs the guided flow: step 1 pickup, step 2 drop-off, then start.

  • Place tiles live under the map. Choosing one updates both the tile and the map pin, and the pickup is locked out during step 2. "Surprise me" picks two random places.
